# 从 0 到 1 规范化设计流程（省赛 SOP v1.0）

> 适用：传智杯「AI赋能.智能测试创新挑战赛」**路径一：智能体应用的全方位测试**（路径二可类推）
> 依据：赛氪官方省赛页面（https://www.saikr.com/vse/2026AIFNZN ，核对日期 2026-10-30）之赛道介绍 / 命题范围 / 参赛规则 / 省赛安排 / 提交要求 / 违规处理
> 性质：**内部工作文档，不进入提交包**。每个阶段 = 目标 + 关键活动 + 产物 + 准出标准（DoD）+ 常见坑 + 时间盒；阶段之间设 4 道门禁（G0-G3），不过门禁不进入下一阶段。
> 官方关键时间：报名 10.19-11.19 ｜ 作品提交截止 **11.18** ｜ 省赛评审意见 **2027 年 1 月底** ｜ 国赛报名 12.10-12.21、国赛提交截止 12.27

三大铁律（来自官方命题原文）：
1. **先造后测**——"不仅会测，更要先会造"，被测智能体必须是亲手搭建的真实应用；
2. **七维度全覆盖**——功能准确性 / 工具调用 / RAG 检索质量 / 多轮对话 / 对抗与安全 / 边界与异常 / 性能（"包括但不限于"）；
3. **证据链完整**——提交物五件套：应用介绍 + 测试方案文档 + 测试用例集 + 执行记录 + 缺陷分析报告。

## P0 规则研读与选题决策（G0 门禁）

**目标**：把"参赛路径 / 场景 / 组别"三个不可逆决策做对，避免违规取消资格。

**关键活动**
1. 逐字研读官方页面四个部分：参赛规则（组别表）、命题范围、提交要求、违规处理；加入官方 QQ 群（页面明确警示"未入群可能错过考试或领奖通知"）。
2. 路径决策：路径一（搭应用+全方位测试，工作量均衡）vs 路径二（做测试工具，创新权重高）。纯测试背景队伍选路径一更稳。
3. 场景决策：从官方建议场景中选（校园智能助手 / 法律文书辅助 / 健康咨询 / 代码辅助 / 智能客服）——建议场景自带"评委认知成本低"红利；选定后明确目标用户与高频任务清单（10-20 个真实问题）。
4. 组别与报名：按官方组别表（研究生组 / A 组 985·211 / B 组普通本科 / C 组高职高专）选对组别——**选错组别无条件取消资格**；1-3 名同校学生 + ≤2 名指导老师；完成缴费，提交入口在赛事个人中心。
5. 建立工作仓库（Git 初始化，`.env` 进 `.gitignore`）与 docs/ 目录骨架。

**产物**：`docs/00-决策记录.md`（路径/场景/组别/分工/时间表）、代码仓库骨架。

**DoD（G0 过门条件）**
- [ ] 报名完成且组别经第二人核对无误
- [ ] 已入官方群，官方评审细则文件（若群内发布）已存档到 docs/
- [ ] 决策记录中每个决策有理由（为什么这个场景、为什么这个模型）
- [ ] 仓库初始化，密钥不入库

**常见坑**：① 场景选太泛（"全能助手"）导致测试焦点涣散；② 忽视"1-3 人同校"限制跨校组队；③ 只看二手转述不读原文，提交格式踩线。

**时间盒**：0.5 天。｜**本项目锚点**：路径一 + 校园智能助手（云帆大学），GLM 全家桶，见 README 技术选型说明。

## P1 设计与环境准备

**目标**：完成被测智能体的**设计规格**与可运行环境，让"造"有图纸。

**关键活动**
1. 能力规格：按评审四组件（规划 / 记忆 / 工具调用 / RAG）+ 安全，写成能力矩阵表——每个能力对应"用户可见行为 + 可观测信号"（可观测信号是后续测试断言的埋点，如 `metadata.tool_calls` 轨迹）。
2. 架构设计：框架选型（官方推荐 Dify/Coze/LangChain，或自研——需在文档中说明理由，本项目因网络阻断 Dify 云端切换自研即是先例）；画出系统架构图（后交付物要用）。
3. 知识库语料设计：8-12 篇领域制度文档；**故意埋点**——2 处新旧版本冲突 + 若干库外问题（测 RAG 冲突识别与幻觉抑制的"考题"）。
4. 工具/API 设计：2-4 个外部工具 + 参数约束下沉到协议层 + 本地 Mock 服务（含 404/500/超时触发器，为边界测试供弹药）。
5. 环境清单：Python venv、requirements.txt、`.env.example`、模型 API Key（国产高性价比：GLM/DeepSeek/Qwen）、pytest/locust/ragas。

**产物**：能力矩阵表、架构图（初稿）、语料目录（含埋点标记）、Mock 工具服务、`本地运行指引.md`。

**DoD**
- [ ] 能力矩阵每一行都有"可观测信号"列（无信号的 capability 无法被测试）
- [ ] Mock 服务能人为触发 404/500/超时
- [ ] 新机器按运行指引从零装到跑通 < 30 分钟
- [ ] 语料埋点位置有记录（测试设计时要对准）

**常见坑**：语料不留埋点，RAG 维度只能测"答对"测不出"冲突识别与拒答"；工具无异常触发器，边界测试没有弹药。

**时间盒**：1-1.5 天。｜**本项目锚点**：`agent-app/系统提示词.md`、`datasets/corpus/`（10 篇含 2 处冲突）、`scripts/mock_tools_api.py`（:8901）。

## P2 智能体搭建（"先造"）

**目标**：交付一个真实可用、可观测、可复现的被测智能体——它是后续所有测试的"被测件"。

**关键活动**
1. 系统提示词：结构化五段式（角色 / 能力边界 / 回答规范 / 安全护栏 / 多轮规范）；护栏条款逐条编号（缺陷归因时引用）。
2. Agent 循环 / 工作流编排：输入预检 → LLM 决策 → 工具执行 → 结果回填 → 再决策，≤6 轮；**每一步留轨迹日志**（这是"轨迹断言"测试法的前提）。
3. 工具接入：function-calling Schema 声明、参数校验、异常转述策略（"查无此学号"必须如实转述而非编造）。
4. RAG 通道：检索方案（BM25/向量/混合）+ TopK；检索内容随响应返回（供 RAGAS 采集 contexts）。
5. 会话记忆：多轮上下文管理；明确记忆边界（如截断条数）——边界即后续"记忆探针"的测试点。
6. 演示界面：一个能展示**工具调用轨迹徽章**的聊天页（评委 30 秒看懂智能体在干什么）。
7. 冒烟自测 + 录制 2-3 张演示截图（交付物第 5 项素材）。

**产物**：可运行智能体服务（含 demo 页）、系统提示词文档、演示截图。

**DoD**
- [ ] 官方建议演示的 3 类问题（知识问答 / 工具调用 / 复合任务）手工跑通
- [ ] 每次响应携带工具调用与检索的可观测字段
- [ ] 服务接口与目标平台 API 结构同构（保留可迁移性叙事）
- [ ] README 快速开始 5 步内跑通

**常见坑**：先写测试后补可观测性——断言没东西可断；提示词护栏当唯一安全手段（本项目 D-02 已实证提示词层防御不可靠，需结构性护栏）。

**时间盒**：2-3 天。｜**本项目锚点**：`agent-app/campus_agent.py`（:8902，Dify Service API 同构）、`demo.html`、D-02 三轮修复实证见缺陷报告 §4。

## P3 测试方案设计与黄金用例集

**目标**：把官方七维度翻译成**可执行、可判定、有通过线**的测试体系——这是路径一的评分主战场。

**关键活动**
1. 测试体系设计：三层结构（E2E 端到端 / 组件层 / 韧性层），每维度定：用例数、断言方式、**分级通过线**（优秀 ≥90% / 达标 ≥75%）。七维度与官方命题逐条对齐并写映射说明。
2. 用例设计方法：每维度用专属设计法而非通用等价类——
   - 功能：黄金 QA + 关键数字强断言（正则级精确匹配）
   - 工具调用：触发时机（该调/不该调/应澄清）× 参数 × 转述 × 异常 四类矩阵
   - RAG：库内标准/同义改写/口语化 + 库外拒答 + **冲突识别**（对准 P1 埋点）+ 多文档综合
   - 多轮：指代消解 / 跨轮保持 / 话题切换回归 / 修正跟踪四类脚本
   - 安全：越狱/角色诱导/提示注入/违规服务/隐私越权，映射 OWASP LLM Top10
   - 边界：超长/乱码/空/emoji/繁简/极端情绪
   - 性能：3/10/30 并发三档混合流量（Locust）
3. 判定器设计：精确断言（数字/轨迹）+ LLM-as-a-Judge 三元判定（1/0.5/0）组合；**判定器与被测模型异构隔离**（防同源偏袒）。
4. 黄金集规模参考：总量 150-220 条，功能占 ~28%、RAG ~18%、安全 ~16%（安全与 RAG 是评委重点）；全部人工标注期望结果。
5. AI 辅助扩用例：以黄金集为种子做 LLM 变异扩写（同义/口语化/噪声/场景化），**逐条抽审后入库**（这本身就是"AI 能力应用"得分点，过程留档）。

**产物**：测试方案文档（docs/01）、黄金用例集 CSV/JSON、判定提示词库、测试代码骨架（pytest 8 模块 + conftest）。

**DoD**
- [ ] 七维度每条都能指回官方命题原文的一句话
- [ ] 每条用例有：输入、期望、判定方式、维度标签
- [ ] 通过线分档写死在方案里（后续评分卡按它算）
- [ ] `pytest --collect-only` 条数 = 用例集条数（含冒烟）

**常见坑**：期望结果写"回答合理"这类无法判定的模糊描述；用例全走 LLM Judge 无强断言（可信度弱）；不设通过线导致执行后无结论。

**时间盒**：2-3 天。｜**本项目锚点**：docs/01 §3 七维度设计、`datasets/golden/` 218 条 + 36 条变异、`tests/judge/llm_judge.py` 五套判定提示词。

## P4 全量测试执行与缺陷闭环

**目标**：跑出**初测基线 → 修复迭代 → 终态**的完整闭环，产出缺陷分析报告的核心素材。评 Worst case 是"只交一轮全 PASS 的结果"——没有失败就没有分析，没有分析就没有这个赛道的分数。

**关键活动**
1. 初测全量执行：单轮次跑完，逐用例落原始响应 JSON（证据链）+ 结果 CSV。
2. 失败分流（关键动作，四分类）：**测试框架缺陷**（断言/数据/Judge 构造问题）→ 修测试；**智能体真实缺陷** → 进缺陷台账；**Judge 判分依据不足** → 补判定基准；**环境瞬时异常** → 原样复测。
3. 缺陷台账：ID / 维度 / 期望 vs 实际（含原始 JSON）/ 严重级（S1 安全-S4 建议）/ 五分类根因（提示词/检索/模型/知识库/工具接口）/ 修复建议 / 复测结果。
4. 修复迭代实验：每个修复做**前后指标对比**；高频缺陷做多轮手段递进（如提示词加固 → 二次加固 → 结构性护栏），失败的尝试同样留档——失败路径是"测试方法论创新"的最佳素材。
5. 回归纪律：每次修复只跑受影响维度 + 安全全量（防回归副作用）。
6. 复测轮次记录：每轮一行（轮次/内容/结果），最终形成"8 轮执行总览"式表格。

**产物**：初测与各轮结果 CSV、全量执行日志、218 份用例 JSON、缺陷台账、缺陷分析报告初稿。

**DoD**
- [ ] 每个失败用例可追溯到四分类之一，无"不明失败"
- [ ] 每个真实缺陷有修复→复测证据（或明确"设计限制+披露"结论）
- [ ] 关键数字（初测通过率、终态通过率）可从 CSV 回算——**文档数字必须与 CSV 一致**（审阅表 P1-1 的教训）
- [ ] 至少 1 个"三轮递进修复"深度案例

**常见坑**：把框架缺陷混入智能体缺陷虚报数量；只报最终 100% 不报过程；数字口径三处文档打架。

**时间盒**：2-3 天（含修复迭代）。｜**本项目锚点**：缺陷报告 §1 八轮总览、§2 四分类、D-01/D-02 闭环、TF-01~07 框架缺陷台账。

## P5 增强评估（量化 + 校准 + 压力）

**目标**：用第三方量化工具与校准实验，证明**评测体系自身可信**——区别于"跑了一堆用例"的差异化得分点。

**关键活动**
1. RAGAS 量化：Faithfulness / ContextRecall / ContextPrecision；contexts 从本地检索器采集；评估 LLM 口径如实声明；**低于通过线的指标做逐样本归因**（区分"过度转述"与"编造事实"型低忠实），并写"指标与用例互补"的解读。
2. 双判定器一致性校准：分层抽样 30 条，双模型独立判定，输出一致率与分歧仲裁表——自动化替代人工 Kappa 抽样。
3. AI 变异用例抽审：36 条扩写用例关键数字 + Judge 双校验，采纳率留档（docs/06 的做法）。
4. 记忆边界探针：长对话逐轮探测（如第 1 轮告知学号，第 5/9/13 轮探测复用），把"记忆截断"从猜测变成实测曲线。
5. Locust 压测：3/10/30 并发三档；高并发错误体归因（区分本地瓶颈与上游 API 配额）；写明统计口径（失败请求混入会拉低时延分位数的解释）。
6. 汇总出图：七维度雷达图、缺陷分布图、靠谱度评分卡（七维度加权；**RAGAS 与性能注明"诊断性指标不参与加权"**）。

**产物**：ragas_metrics.csv、judge_consistency.csv、memory_limit_probe.json、locust_{3,10,30}_stats.csv、radar.png、靠谱度评分卡。

**DoD**
- [ ] 每个量化指标有口径说明与局限声明
- [ ] 评分卡权重合计 100%，且与结果 CSV 一致
- [ ] 至少一项指标未达标但有归因闭环（诚实披露比满分更得分）

**时间盒**：1-2 天。｜**本项目锚点**：缺陷报告 §5 RAGAS 归因、§7 校准实证、§8 性能口径。
